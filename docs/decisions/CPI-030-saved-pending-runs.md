# CPI-030 — Save pending attempts without forfeiting earned rewards

## CPI-029 revive flow and delivery boundary

The injected rewarded flow shows the next continuation ordinal and the exact replacement SP before the user chooses to watch: 200 SP for applied continuations 1–5, then 150 for 6–10. Its server view keeps granted, applied and score-attribution counts separate. Provider earned/closed events cannot mint a grant; the flow waits for the trusted verified status, closes fullscreen before gameplay resumes, and explicitly applies the original grant through the serialized ranked command queue. No-fill, offline, privacy unavailable and ambiguous verification retain fixed, actionable states. A shared native-adapter arbiter prevents overlapping fullscreen requests. The permit must match the complete approved SDK/mediation inventory and privacy flags before SDK initialization or load.

The default native adapter is unavailable, and App services remain absent unless explicitly supplied. The owner has not approved live account capture or ads. No live SDK/plugin, ad-unit IDs, consent transport, provider keys, hosted handler or privacy/store declarations are supplied or approved here. Tests must not be described as live AdMob or store-review evidence.

## Retained pending attempts

An unresolved ad verification can outlive the foreground attempt. The user may explicitly save a dead attempt that has a pending reward or an earned, unapplied grant, return to the menu, and start another ranked attempt. Saving does not end the old attempt, finalize its score, discard its reward ledger, or consume a revive.

`lease_active` separates the attached attempt from retained recovery history. The database permits at most one attached unfinished attempt per account. An inactive attempt cannot accept gameplay commands or reward application. A late verified callback can still issue the original grant and checkpoint while preserving the inactive flag. Explicit authenticated recovery reattaches it only after the current attached attempt has ended; it preserves the original private RNG and resources.

`POST /ranked/archive` accepts only the current run ID, exact sequence, idempotency key and current device lease. The account subject and device identity come from the trusted authentication callback. It locks the common account owner first, then the run, rotates the capability, and writes checkpoint, audit and receipt in one transaction. Ambiguous network outcomes retry the exact command. A matching durable receipt returns an acknowledgment containing only the archived run ID. No client can archive another account's run by supplying an owner field.

`POST /ranked/saved` returns one page of at most 20 own inactive unfinished attempts, using a descending creation-time/UUID keyset. Timestamps retain PostgreSQL microseconds. The allowlist contains the opaque run ID, ruleset, dead/pending state, last cleared row and granted/applied counts. It excludes the RNG, route, lease, profile, reward provider identifiers and other accounts. Responses use no-store and are never persisted on the device. The same client observes the session owner's opaque account scope; signing out synchronously hides the old list and aborts its request.

The saved-attempt panel displays a bounded page, refreshes on request, and offers explicit recovery only when no unfinished attempt is attached. The ranked client confirms server archive acknowledgment before clearing its local projection. Guest practice remains local and independent. Hosts must explicitly mount the trusted pending routes at the same configured base path as the client; no service is configured or enabled by this source change.

Validation covers database uniqueness and immutable retained reward rows, rollback/idempotency and capability errors, exact large progress and timestamp paging, account-switch fencing, and the signed synthetic callback walkthrough: save R1, start R2, receive R1's late grant while inactive, finish R2, then recover and apply R1's original grant. Synthetic signatures and disposable PostgreSQL fixtures provide implementation evidence; they do not demonstrate live ad-network delivery or approve production services.
